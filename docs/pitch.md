# Forte Review — текст и порядок демонстрации

## Короткий питч, около двух минут

Мы сделали Forte Review — сервис проверки кассовых операций по видео. Загружаем MOV, получаем возможное нарушение, время события, кадры из исходной записи и правило, на которое опирается вывод. Сразу покажем этот путь.

Здесь отправляем запись через интерфейс. Сервер принимает её по защищённому API, запускает анализ и возвращает результат. В результате можно перейти к моменту события, увеличить подтверждающие кадры и открыть нормативный источник. Если обработка не удалась, сервис показывает ошибку, а не объявляет запись нормальной.

Внутри работает Qwen3-VL-2B на нашем ноутбуке с RTX 4060. Мы обучили небольшой LoRA-адаптер на ручных описаниях 26 тренировочных видео. Модель описывает видимые роли, предметы и действия. Затем локальный поиск подбирает правила из подготовленной базы, а модель проверяет их условия и исключения по кадрам. Для найденного события выполняется повторная проверка на более плотной последовательности кадров.

Мы разделили данные на обучение, валидацию и отложенную проверку. На семи валидационных видео выбранная версия получила F1 0,667. На семи отложенных видео после фиксации модели F1 составил 0,444: два найденных положительных видео, три ложных срабатывания и два пропуска. Это показывает, что обобщение ещё слабое. Мы не выдаём валидационный результат за точность на новых записях. Точное время, тип события и применимость правила требуют проверки человеком.

Наш результат — работающий полный путь от новой записи до проверяемого вывода: интерфейс, локальная модель, база правил, реальные кадры и публичный API с ключом доступа. Модель не идентифицирует людей и не использует облачные AI-сервисы. Forte Review помогает проверяющему найти и разобрать важный момент; окончательное решение остаётся за человеком.

## Как показывать

1. Открыть публичный адрес из [инструкции для судей](judges-handoff.md), ввести ключ вне записи экрана. Не выводить ключ на слайд.
2. Использовать согласованный командой тренировочный пример. Не показывать приватное видео широкой аудитории без разрешения организаторов. Для открытой записи демонстрации использовать явно помеченный синтетический пример.
3. Показать загрузку, статус, итог, кадр и источник. Заранее проверить, что выбранный пример действительно подходит для этой демонстрации; не выдавать его за независимую оценку качества.
4. Пока запрос обрабатывается, объяснить локальную модель и проверку правил. Не обещать мгновенный ответ.
5. Открыть [итоговый отчёт](release-results.md) с отложенной проверкой и фактическими API-временами. Эти цифры важнее старого слайда с одним процентом.

## Короткие ответы на вопросы

- **Почему 2B, а не 4B или Bonsai?** Выбирали по завершённой валидации. Проверенные 4B-варианты пропустили все положительные валидационные видео; большая модель не дала лучшего результата. Bonsai остался историческим сравнением и не обслуживает API.
- **Обучалась ли модель?** Да: четыре эпохи QLoRA на ручных описаниях тренировочных видео; базовые веса и зрительный энкодер заморожены. Низкая ошибка обучения сама по себе не доказывает качество, поэтому мы сравнили полный процесс на валидации.
- **Что означает пустой список?** Модель не подтвердила нарушение по своим проверкам. Это не гарантия отсутствия нарушения: на валидации есть пропуск. Ошибка обработки имеет отдельный статус `failed`.
- **Новые правила и новый ракурс?** Поиск может выбрать правило, которого не было в тренировочных описаниях. Надёжность на невиданных типах нарушений и новых ракурсах ещё не доказана.
- **Где слабое место?** Малый объём размеченных видео, пропуски, ложные срабатывания и точность момента события. Следующий этап — согласованная разметка событий и условий правил, новые камеры и независимая проверка, а не подбор настроек по финальному тесту.
- **Как судьи проверяют?** MOV отправляется в `POST /api/v1/analyze` с `X-API-Key`; результат получается через `GET /api/v1/jobs/{job_id}`. Адрес и ключ передаются организаторам приватно по правилам подачи.
