Обновление: backend и native Bonsai запущены отдельными пользовательскими systemd-службами на ноутбуке Ратмира; реальные positive/negative train-загрузки прошли через API. Публичный доступ пока не подтверждён, качество модели недостаточно для соревнования.

Исходная интеграционная ревизия: `158b541`. Точный коммит этого обновления — последний коммит с этим документом в Git. Проверяемая среда: Windows, Python 3.11.0, core requirements; ноутбук с MX250 2 ГБ. RTX 4060 находится у Ратмира, настоящая модель ещё не готова.

## Выполненная работа

1. При запуске API модель загружается в отдельном процессе и обрабатывает три синтетических кадра. Для NPZ проверяются численные значения, схема классов и соответствие правилам. Demo/weak-веса не проходят режим reference. Для Qwen/Bonsai вызывается настоящая сессия и проверяется формат ответа. GPU-путь реализован, но здесь не запускался.
2. `/health` показывает работоспособность сервера и диагностику, `/ready` возвращает 200 только после успешной проверки модели, иначе 503. Поле `model_present` оставлено для совместимости; интерфейс использует `ready`. Замена модели/каталога требует перезапуска и повторной проверки. Проверка старта ограничена 90 секундами (настройка `FORTE_READINESS_TIMEOUT`, максимум 120).
3. Один runtime принадлежит одному API-процессу: второй сервер с тем же каталогом не стартует. Сохраняется один слот обработки; перегрузка возвращает 429 и `Retry-After: 5`.
4. Остановка сервера завершает его дочерний обработчик. Обрыв служебного канала также завершает обработчик при аварийной остановке родителя. Это не распространяется на отдельно запущенный llama.cpp/Bonsai server.
5. После обработки временные видео/JSON удаляются. Если Windows блокирует файл, слот всё равно освобождается, очистка повторяется каждые 5 секунд; `/health.cleanup_pending_files` показывает остаток. При перезапуске незавершённые задания становятся `failed`, их временные файлы и осиротевшие загрузки очищаются. Готовые результаты с JPEG сохраняются в SQLite под защитой API-ключа.
6. Исправлено чтение кириллических путей в инструментах CPU-оценки через явный UTF-8. Слабая бинарная модель остаётся экспериментом и не подключена к нормативному API.

## Запуск и восстановление

Windows, из корня репозитория, после установки core requirements:

```powershell
# Демонстрация: отдельные ключ и хранилище.
.\scripts\serve.ps1 -Engine demo -Port 8001 -Runtime runtime/public-demo
# Настоящая модель: только после завершения установки на RTX-хосте.
.\scripts\serve.ps1 -Engine qwen -Model models/qwen3-vl-2b -Runtime runtime/jury -Port 8000
```

При другой среде передайте `-Python <путь-к-python.exe>`. Ключ создаётся в `<runtime>/access-key.txt`; скрипт печатает путь, а не значение. Повторный запуск использует тот же ключ. Ключ не коммитить. Дождитесь `GET /ready` → 200 прежде, чем давать доступ жюри. При 503 смотрите `readiness.code`: `model_missing`, `dependencies_missing`, `model_invalid`, `probe_timeout`, `probe_failed` или `restart_required`. Наличие файла весов не гарантирует успешную загрузку или качество.

Для штатного завершения нажмите Ctrl+C в терминале сервера. Для восстановления запустите ту же команду с тем же runtime. Прерванные видео загрузите заново. Для смены модели остановите процесс, обновите веса/настройки и запустите снова. Не удаляйте SQLite ради перезапуска. Старые JPEG остаются в базе до отдельной согласованной очистки после мероприятия.

## Публичный доступ

Фактическая проверка на текущем ноутбуке: оба локальных сервера готовы, все 81 Python/API и 11 frontend-тестов прошли. Живой HTTP-цикл на 8001: normal 1,312 с, event 1,485 с, multiple 1,265 с, corrupt → failed за 0,953 с; ключи изолированы, JPEG декодируются, исходные загрузки удалены. Подробности в `TEST_REPORT.md`.

Cloudflare 2026.5.2 получил временные адреса, но подключение не установилось: QUIC timeout, HTTP/2 TLS на 7844 обрывается. Публичный `/ready` не прошёл. Публичный этап пока **не завершён**. Владелец выбрал повторную проверку на ноутбуке Ратмира; неработающий туннель здесь остановлен. По [документации Cloudflare](https://developers.cloudflare.com/tunnel/configuration/) для обоих протоколов требуется исходящий порт 7844. Сетевые настройки и firewall не менялись.

Владелец команды подтвердил разрешение организаторов на Cloudflare Tunnel. Публикуйте API, который уже прошёл `/ready`. Туннель для синтетической демонстрации направляется на отдельный порт 8001, а сервер реальной модели — на 8000:

```powershell
cloudflared tunnel --url http://127.0.0.1:8001 --no-autoupdate
```

В случае недоступности UDP можно повторить с `--protocol http2`. URL берётся из вывода cloudflared. Не добавляйте email/PIN-вход перед API жюри. По [официальной документации](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/) адрес временный, меняется при пересоздании и работает только пока жив процесс; гарантий доступности нет. Стабильный named tunnel требует отдельной настройки аккаунта/домена. Текущий временный адрес и ключ выдаются владельцу отдельно, не сохраняются в Git.

Проверка через публичный URL, ключ в локальном окружении:

```powershell
$env:FORTE_API_KEY=(Get-Content runtime/public-demo/access-key.txt -Raw).Trim()
.venv\Scripts\python.exe -m scripts.smoke_api data/demo/multiple.mov --url https://YOUR-HOST.trycloudflare.com
```

Успешный GET главной страницы не заменяет POST → polling → done. Повторите проверку с другого подключения. Не выключайте ноутбук/сервер/туннель во время показа.

## Передача Ратмиру и следующий этап

Передать `team/RATMIR_BACKEND_INTEGRATION.md`. Он продолжает в своей копии на RTX 4060; SSH-адрес пока не задан. Не менять его окружение вслепую: в `docs/ml-handoff.md` уже описана отдельная среда с CUDA. Текущая ветка не содержит готовых весов.

Когда модель готова: положительный, отрицательный и много-событийный примеры через API; проверка 1–3 JPEG на событие человеком; три холодных запуска длинного видео; замер времени от начала загрузки до `done`; локальная работа без внешней сети; затем разрешённый публичный endpoint. Цель <240 секунд, официальный предел 300. Итоговые validation/test-метрики фиксируются отдельно от технической готовности.

На этом ноутбуке слабый CPU baseline на train-ролике 142,533 с занял 17,866 / 12,986 / 11,940 с в новых Python-процессах; это **не полный API и не Qwen/GPU**. Validation: TP=3, TN=1, FP=3, FN=0 на 7 уникальных видео; слишком много ложных тревог. Test не запускался. Настоящая модель, её качество, VRAM, публичная скорость на реальных данных и работа на другом сетевом подключении остаются обязательными проверками до подачи.
