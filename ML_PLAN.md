На устранение проблем установки Qwen — максимум 45 минут; для Bonsai также максимум 45 минут. Неуспешный кандидат исключается из текущего сравнения, остальные работы продолжаются.

**Подготовка данных**

- Распаковать архив в игнорируемую папку. Импортировать бинарные метки и время, сохраняя исходные значения для локальной сверки.
- Каждый участник просматривает примерно 14 видео локально. Добавляет тип, интервал, опорное время, явные нормальные интервалы и неопределённость. Частные описания остаются в локальных файлах.
- Группировать связанные записи по сессии, камере и участникам. Проверять точные дубликаты по SHA-256; близкие записи группировать при ручном просмотре.
- Стремиться к 60/20/20 — примерно 25/8/9 видео. Целостность групп важнее точного количества. Закрепить split до обучения.
- Словарь поддерживаемых классов формировать по train и проверенным нормативным основаниям. Неподдерживаемые события в validation/test учитывать как ограничения и пропуски.
- Не превращать время вне положительной отметки в отрицательную разметку. При перекрытии разных событий использовать многометочные цели для baseline; не выбирать один класс произвольно.

**ML-код и интерфейс**

- Сохранить `analyze(path, model, engine, rule_path, progress)` и существующую схему результата.
- Добавить проверку manifest: пути, интервалы, метки, группы, дубликаты, полнота оценочной разметки.
- Сохранить полное временное покрытие. Проверить реальные timestamps, обработку конца ролика и объединение событий между окнами.
- Для Qwen проверить корректность ограничений визуальных токенов и обнаружение обрезанного ответа.
- Для Bonsai добавить отдельный адаптер с тем же внутренним форматом событий. Локальный рантайм доступен только через loopback; backend-владелец интегрирует `engine=bonsai`, запуск и остановку процесса.
- Ошибки декодирования, модели, JSON, OOM и таймауты остаются ошибками обработки. Неизвестные rule ID отклоняются.
- Изменения общих зависимостей согласовывать с backend-владельцем. Маршруты и frontend остаются в ответственности коллег.

**Оценивание и выбор**

Дополнить оценщик проверкой утечек между всеми split, раздельными причинами отказов, метриками по классам и однозначным сопоставлением событий. При ошибке обработки ожидаемые события должны учитываться в общей полноте как необнаруженные; метрики успешно обработанных видео выводятся отдельно.

Выбирать по **F1 событий с учётом типа и внутреннего допуска 3 секунды** среди кандидатов, проходящих ограничения времени и стабильности. При равенстве — по F1 видео, затем по меньшей холодной задержке. Допуск 3 секунды явно обозначить как внутренний, не официальный.

Цель по скорости — холодный анализ самого длинного клипа до 240 секунд; полный API-цикл должен укладываться в 300 секунд. Сначала измеряем длинный train-клип, чтобы не использовать test для настройки.

## 4. Проверки и критерии готовности

- Синтетика: нормальное видео, одно и несколько событий, разные классы, перекрывающиеся окна и границы ролика.
- Manifest: утечка групп, дубликаты, неправильное время, неоднозначные интервалы и неподдерживаемые классы.
- Результат: 1–3 JPEG на событие, timestamp реального кадра, разрешённый источник правила, сохранение нескольких событий.
- Отказы: отсутствующие веса, недопустимый JSON, неизвестный rule ID, OOM, таймаут и неполное декодирование никогда не дают чистый вердикт.
- Реальные данные: TP/TN/FP/FN, event TP/FP/FN, precision/recall/F1, число отказов, ошибки времени и знаменатели.
- Производительность: холодная загрузка, полный анализ, пик VRAM и RAM; для самого длинного validation-клипа — три холодных запуска.
- Обобщение: отдельный ракурс, если он есть. Кропы и повороты описывать только как стресс-тесты.
- Offline: после загрузки весов выполнить анализ без внешнего доступа.
- Финальный test оценить один раз после фиксации модели. Результаты test не использовать для последующей настройки.

Работаем **12 продуктивных часов**, разметку делят трое. Приоритет — максимальное измеренное качество при соблюдении времени обработки. Brev не входит в основной план.

Передаём:

- конфигурацию inference, версии, SHA-256 и лицензии;
- команды подготовки, обучения, оценки и запуска под Linux;
- агрегированные validation/test-отчёты и измерения ресурсов;

Baseline сохраняется как резерв, но его качество также должно быть измерено. Если ни один кандидат не показывает полезного качества, фиксируем это прямо: успешная загрузка модели и правдоподобный ответ не считаются выполнением ML-задачи.
